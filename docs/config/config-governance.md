# 配置治理规则

本文件用于定义当前仓库的配置治理边界，避免在后续清洗过程中继续扩大历史坏边界。

## 1. 当前阶段原则

- 先说明，不盲目改值
- 先分层，再迁移
- 先识别敏感项，再脱敏和外置
- 不在未确认运行方式前合并配置

## 2. 推荐配置分层

### 公共配置 `application.yml`

建议只保留：

- Spring Boot 基础配置
- Web 容器基础配置
- 日志框架公共配置
- Jackson、MVC、线程池等通用配置
- 安全框架基础开关
- 文档工具基础配置

不建议继续放入：

- 数据库地址与口令
- Redis 地址与口令
- 邮件账号和密码
- 第三方平台 `appid` / `secret`
- 微信支付商户参数
- 生产域名回调地址

### 环境配置 `application-dev.yml` / `application-prod.yml`

建议承载：

- 数据源连接信息
- Redis 连接信息
- 第三方环境差异参数
- 监控地址
- 外部服务地址

### 外部注入配置

后续应优先迁移的配置：

- 数据库口令
- Redis 口令
- API 密钥
- 微信支付密钥和商户参数
- 短信/邮件/OSS 第三方凭据

## 3. 当前已识别的敏感配置类型

- 数据库账号口令
- Redis 账号口令
- API 加解密密钥
- 微信小程序 `appid` / `secret`
- 微信支付商户参数
- Docker 中 MySQL / MinIO 默认口令

说明：

- 本轮不直接改动这些值
- 后续批次应先处理“说明 + 样例化 + 外部注入”

## 4. 后续迁移建议

建议按以下顺序推进：

1. 把敏感配置从 README 和说明文档中清理掉
2. 为 YAML 中的敏感项建立“样例值 + 注入说明”
3. 将生产口令迁移到环境变量或运维注入
4. 为主应用、监控中心、SnailJob 分别整理独立配置说明

## 5. 配置新增约束

后续新增配置时遵循：

- 不允许新增硬编码生产口令进入仓库
- 不允许通过注释切换数据库地址作为正式方案
- 不允许继续把鲜花专属业务参数混入公共配置
- 不允许新增 `flower` / `folwer` 命名的核心商城配置前缀

## 6. AI Harness 化要求

配置治理不仅服务于部署，也服务于 AI 理解。

因此后续应尽量做到：

- 配置职责可解释
- 环境差异可枚举
- 敏感项与非敏感项可区分
- 主应用与扩展服务配置关系可追踪
