# 检测与测试基线

本文件用于定义当前仓库的“可验证基线”。

目标不是一开始就补齐自动化测试，而是先把“系统现在正常”的判断标准沉淀到仓库内，供后续人工、脚本和 AI 共同使用。

## 1. 为什么要先做基线

当前项目属于遗留系统清洗，不是从零开发。

这意味着：

- 原系统大概率已经具备一条可运行主链路
- 后续所有整理和重构都应以“不要破坏现有可用能力”为前提
- 如果没有基线，AI 和人工都无法判断改动是否引入回归

因此，本仓库后续改造必须配套：

- 启动基线
- 接口基线
- 业务链路基线
- 回归清单

## 2. 当前已识别的可验证入口

### 启动入口

- `ruoyi-admin`
- `ruoyi-monitor-admin`
- `ruoyi-snailjob-server`

### API 文档入口

- Swagger UI：`/swagger-ui.html`
- OpenAPI：`/v3/api-docs`

### 关键业务接口前缀

- 后台：`/flower/*`
- 小程序：`/flowerapplet/*`
- 支付回调：`/wxpayback/*`
- 认证：`/auth`

说明：

- 当前接口前缀存在历史不统一问题，这正是后续治理对象。
- 在治理前，应先把这些入口当作“现状基线”而不是先改名。

## 3. 当前自动化测试现状

现有测试主要位于：

- `ruoyi-admin/src/test/java/org/dromara/test`

已识别测试类：

- `AssertUnitTest`
- `DemoUnitTest`
- `ParamUnitTest`
- `TagUnitTest`

结论：

- 当前自动化测试偏示例性质
- 对商城核心业务回归帮助有限
- 不足以覆盖订单、商品、支付、物流、会员、积分等主链路

## 4. 当前建议的验证层次

后续改造时至少按以下层次执行验证：

### 第 1 层：静态与构建验证

- Maven 编译
- 模块打包
- 配置文件结构检查

### 第 2 层：启动验证

- 主应用可启动
- 监控中心可启动
- SnailJob 服务端可启动

### 第 3 层：接口冒烟验证

- 登录接口可用
- Swagger 页面可访问
- 商品/分类/订单核心接口可访问

### 第 4 层：业务链路回归

- 商品浏览
- 购物车
- 下单
- 支付回调
- 订单查询
- 退款/售后基础链路

## 5. 后续落地方向

短期：

- 先使用文档清单做人工和半自动验证

中期：

- 增加可执行的启动验证命令
- 增加接口冒烟脚本

长期：

- 为标准商城主干补自动化测试
- 将回归清单逐步脚本化

## 6. 使用原则

- 所有批次改动前，先明确影响哪些基线项
- 所有批次改动后，至少回归对应清单
- 未验证的能力，不应默认认为“未受影响”
